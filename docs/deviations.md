# Deviations

Where behaviour differs between platforms, and where a design decision was made
rather than inherited.

The package hides what it can. This page is what is left: differences that
cannot be hidden without either lying about what happened or paying a cost out
of proportion to the benefit. Anything here is a thing to check if a program
behaves differently on two systems.

## Event differences between backends

### Windows cannot distinguish a write from a permission change

Windows reports a single "modified" action for a change to contents,
attributes, or security alike. Once the notification arrives, the three are
indistinguishable.

The only evidence available is the filter requested when the watch was
registered, so a watch that asked for `Write` reads the action as `Write`, and
one that asked only for `Chmod` reads it as `Chmod`. **A watch that asked for
both cannot tell them apart** and will see `Write`.

Elsewhere the two are separate kernel events and are reported accurately.

### A rename out of a watched directory

Moving a file *out* of a watched directory, to somewhere unwatched:

- **inotify and fanotify** report `Rename`, because the kernel says the name
  was moved rather than deleted.
- **kqueue** reports `Rename` when the file's own descriptor was open — which
  is the case when the watch asked for `Write` or `Chmod` — and `Remove`
  otherwise, because a directory listing alone cannot tell the two apart.
- **polling** reports `Remove`, for the same reason: from one scan to the next,
  a file that moved away and one that was deleted look identical.

Renames *within* a watched directory are reported as `Rename` on the old name
and `Create` on the new one everywhere.

### Polling cannot see what does not last

The polling backend compares snapshots, so anything that begins and ends
between two scans never happened as far as it is concerned. A file created and
deleted within one interval is not reported at all.

It also cannot report opens, reads, or closes, since those leave no trace in
the metadata it compares, and it will miss a modification that changes neither
size nor timestamp — rare with nanosecond timestamps, real on filesystems with
one-second granularity.

These are properties of watching by comparison, not defects. A backend that
hears from the kernel does not have them.

### inotify ignores files that have been unlinked but are still open

Requested deliberately, with `IN_EXCL_UNLINK`. Without it, a file that has been
deleted while a process still holds it open goes on producing events under a
name that no longer exists.

No other backend can observe such a file at all, so excluding it makes
behaviour consistent across platforms as well as being less confusing on its
own terms.

### fanotify and Windows watch directories, never single files

Both interfaces mark directories. A watch on a single file is therefore a mark
on its parent with every other name discarded.

The visible consequence is cost rather than correctness: watching one file in a
large, busy directory means the kernel reports the whole directory and this
package throws most of it away.

## Recursion

### Contents of an adopted directory are reported by this package, not the kernel

When a directory appears inside a recursive watch, anything already inside it
existed before any watch could cover it, and the kernel will never report those
files. This package walks the new directory and reports what it finds.

Those `Create` events are therefore *synthesised*. They are indistinguishable
from real ones by design, and the alternative — an entire subtree silently
unwatched, which is what happens when a populated directory is renamed in
atomically — is far worse.

A consequence: for a moment after a directory appears, events for its contents
are generated by a walk rather than delivered by the kernel, so their ordering
relative to other events is not meaningful.

### Overlapping recursive watches deliver once

Two recursive watches covering the same file report a change to it once, not
once per watch. Kernel backends behave this way naturally, since they report a
change to a *file*; the polling backend was changed to match, because a caller
should not be able to tell which backend they are using by counting events.

Watches shared between two overlapping recursive roots are reference-counted,
so removing one root leaves the other's coverage intact and the last one to go
releases it.

## Descriptor budget

On backends that spend a descriptor per watched file, the budget stops watching
consuming every descriptor in the process. Files that cannot be given one are
compared on an interval instead, so every operation is still reported — but
modifications arrive **up to one interval late** rather than immediately, and a
modification that is undone within one interval is not seen at all.

Creation, removal and renaming are unaffected: those come from the directory,
which always has a descriptor.

`Watcher.Stats().DescriptorsDenied` reports how often the budget was reached.
A non-zero value means some files are being observed by comparison rather than
by notification, which is a difference in latency and in what a rapid
change-and-revert looks like, not in which operations are reported.

## Locking

### Advisory on Unix, mandatory on Windows

On Unix a lock coordinates processes that ask, and does nothing to one that
simply opens the file and writes. On Windows the lock is enforced by the
operating system: an unrelated process's read or write inside a locked range
fails.

This is a behavioural difference, not a stricter shade of the same thing. Code
that works on Unix because a non-participating writer is ignored will see that
writer's calls fail on Windows. Write as though every participant cooperates,
because on Unix it must.

`lock.IsMandatory()` reports which applies.

### Shared locks are exclusive on Plan 9 and WebAssembly

Those platforms have no locking syscall, so locks are taken by creating a file
exclusively. That cannot express "several holders, but no writer", so a shared
lock is granted as an exclusive one.

Granting a stricter lock than was asked for costs concurrency and never
correctness. What it cannot do is survive its holder dying — see
[platform-notes.md](platform-notes.md).

## Decisions taken deliberately

### FSEvents is excluded, not deferred

macOS FSEvents requires CoreFoundation, and therefore cgo. This module is pure
Go: `CGO_ENABLED=0` builds and clean cross-compilation to every supported
target are worth more than what FSEvents would add over kqueue.

Recorded so it is not revisited by accident.

### fanotify permission events are out of scope

fanotify's permission classes let a program hold up every file access on the
system until it answers. That is a different and considerably more dangerous
kind of tool than a file watcher — a bug in it hangs the machine — and it does
not belong behind the same API.

### There is no `sync`-shaped lock wrapper

A `Mutex` with `Lock()` and `Unlock()` taking no arguments and returning no
errors would be familiar, and that is exactly the problem. A file lock can fail
in ways `sync.Mutex` cannot: the filesystem can refuse, the file can vanish, a
network mount can lie. An API shaped like `sync` would have to hide those or
panic, and code written against it would look correct while ignoring failures
that matter.

The context-taking API is slightly less convenient and does not encourage that
mistake.

### Waiting for a lock retries rather than blocking

A goroutine parked in a blocking lock syscall cannot be interrupted by a
context. Acquisition therefore retries with backoff, which costs up to one
retry interval of latency and makes cancellation actually work.

## Case-insensitive filesystems

APFS and NTFS treat `Foo.txt` and `foo.txt` as one file, and events report
whichever spelling the change used — not necessarily the one passed to `Add`.
Compare paths case-insensitively on those systems, or normalise first.

This package does not normalise on your behalf, because it cannot know whether
a given path lives on a case-sensitive filesystem without asking, and asking
per event would cost a syscall to fix a problem most programs do not have.
